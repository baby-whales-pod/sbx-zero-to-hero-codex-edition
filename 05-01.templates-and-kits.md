# Templates & kits — add your own tools
> `sbx` without ai governance policy

> [!NOTE]
> In this lesson you will build two kits — a **builder** that installs your own tools and a **launcher** that starts a service — attach both to a sandbox with `--kit`, add a kit to a running sandbox, and share a kit as a ZIP, an OCI artifact, or from a git repo.

A **kit** is a small declarative artifact (a folder with a `spec.yaml`) that extends a sandbox with extra tools, files, environment variables, network rules, and startup commands — **without** rebuilding an image by hand.

In this lesson we build **two** simple kits:
1. a **builder** kit that *installs* your own tools (`setup.install`)
2. a **launcher** kit that *starts* a service (`setup.startup`)

Then we attach both to a sandbox with `--kit`.

> ℹ️ `sbx kit` is **experimental** — flags may change between releases. The kits below use the **v2 kit schema** (`schemaVersion: "2"`).


## 1. Create the builder kit

A builder kit runs its `setup.install` **when the sandbox is created** (think of it as the "build" step). Here it installs `figlet` and `python3`.

```bash
mkdir -p kits/tools-kit
```

Create `kits/tools-kit/spec.yaml`:

```yaml
schemaVersion: "2"
kind: mixin
name: tools-kit
displayName: Tools Kit
description: |
  Builder kit: installs my own tools into the sandbox at creation time.

# apt has to reach the Ubuntu archives. 
permissions:
  network:
    allow:
      - archive.ubuntu.com:80
      - archive.ubuntu.com:443
      - security.ubuntu.com:80
      - security.ubuntu.com:443
      - ports.ubuntu.com:80
      - ports.ubuntu.com:443

setup:
  install:
    - command: |
        set -e
        if command -v figlet >/dev/null 2>&1 && command -v python3 >/dev/null 2>&1; then
          exit 0
        fi
        apt-get -o DPkg::Lock::Timeout=600 update -qq
        apt-get -o DPkg::Lock::Timeout=600 install -y --no-install-recommends figlet python3
      user: "0"
      description: Install figlet (+python3), waiting out the base image's own apt

```

> [!IMPORTANT]
> **Why `DPkg::Lock::Timeout`?** The kit's `install` runs while the base image is still doing its own `apt-get`, so the two collide on the apt/dpkg locks (`Could not get lock /var/lib/apt/lists/lock`) and a plain `apt-get install` fails intermittently. `-o DPkg::Lock::Timeout=600` makes apt **wait** for the lock instead of erroring out — the same trick sbx's own experimental `docker` kit uses. No retry loop needed.

> [!TIP]
> `install` commands default to `user: "0"` (root) — the explicit `user: "0"` above is just documentation. `startup` commands default to `user: "1000"` (the `agent` account) instead.

> [!TIP]
> `install` runs **once** at creation, but it runs again for every `sbx kit add`, so the spec asks you to make it idempotent — hence the `command -v` guard. (`setup.files` has an `onlyIfMissing: true` for the same reason.)

> [!TIP]
> `python3` is already baked into the `codex-docker` base image (along with Go, Node, Java…), so strictly speaking only `figlet` needs installing — we keep `python3` here to make the dependency on the launcher kit explicit. Installing an already-present package is a harmless no-op.

Validate and inspect it:

```bash
sbx kit validate ./kits/tools-kit
sbx kit inspect  ./kits/tools-kit
```

## 2. Create the launcher kit

A launcher kit runs its `setup.startup` **every time the container starts**. Here it serves the workspace over HTTP, in the background, on port `7070`.

```bash
mkdir -p kits/serve-kit
```

Create `kits/serve-kit/spec.yaml`:

```yaml
schemaVersion: "2"
kind: mixin
name: serve-kit
displayName: Serve Kit
description: |
  Launcher kit: starts a tiny HTTP file server in the background at startup.

ports:
  - container: 7070
    protocol: tcp
    name: serve-kit

setup:
  startup:
    - command:
        - sh
        - -c
        - |
          pidfile=/tmp/serve-kit.pid
          if [ -f "$pidfile" ] && kill -0 "$(cat "$pidfile")" 2>/dev/null; then
            echo "serve-kit: already serving port 7070 (pid $(cat "$pidfile"))"
            exit 0
          fi
          echo $$ > "$pidfile"
          exec python3 -m http.server 7070 --bind 0.0.0.0 --directory "${WORKSPACE_DIR:-/}"
      user: "1000"
      background: true
      description: Serve the sandbox workspace over HTTP on port 7070

```


```bash
sbx kit validate ./kits/serve-kit
```

## 3. Create a sandbox with both kits

`--kit` can be repeated. The builder installs the tools, the launcher starts the server:

```bash
sbx run codex . \
  --kit ./kits/tools-kit \
  --kit ./kits/serve-kit \
  --name codex-kits

```

## 4. Check the builder kit worked

The tool your builder kit installed is now available:

Try this in a terminal:
```bash
sbx exec codex-kits -- figlet "SBX kits"
```

Ask the agent too:

```text
please run: figlet "hello from a kit"
```

## 5. Check the launcher kit worked

The launcher started an HTTP server on `7070` inside the sandbox. Because the kit declares a `ports` entry, sbx already published it — on a **random** host port bound to `127.0.0.1`:

```bash
sbx ports codex-kits
```

Pin it to `7070` on the host to get a stable URL:

```bash
sbx ports codex-kits --publish 7070:7070/tcp
curl http://127.0.0.1:7070/
# -> an HTML directory listing of the workspace
```

> ✋ Use `127.0.0.1`, **not** `localhost`. Python's `http.server` listens on IPv4 only (`0.0.0.0`), while `sbx ports` publishes on both `127.0.0.1` and `[::1]`. On macOS `localhost` resolves to the IPv6 `::1` first → the request hits the IPv6 side, finds no listener in the sandbox, and returns `curl: (56) Connection reset by peer`. `127.0.0.1` forces IPv4 and works. (Alternatively, publish IPv4-only: `--publish 127.0.0.1:7070:7070/tcp`.)

Unpublish when done:
```bash
sbx ports codex-kits --unpublish 7070:7070/tcp
```

## 6. Bonus — add a kit to a *running* sandbox

You do not have to recreate a sandbox to add a kit. Inject one live with `sbx kit add`:

```bash
# add the launcher kit to the sandbox from an earlier lesson
sbx kit add codex-hello-sbx ./kits/serve-kit
```

## 7. Publish & share a kit

> 📖 Reference: <https://docs.docker.com/ai/sandboxes/customize/kits/>

Unlike a **template** (a baked image shared as a `.tar`, see `05-02`), a **kit** is a small declarative artifact — so it travels well. There are three ways to share it.

### a) As a ZIP file (simplest)

Package the kit directory into a portable ZIP and hand it over (drive, CI artifact, email…):

```bash
# package the folder into a ZIP (default name: <name>.zip)
sbx kit pack ./kits/tools-kit -o tools-kit.zip

# a teammate reuses it directly
sbx run codex . --kit ./tools-kit.zip --name codex-fromzip
```

### b) Via an OCI registry (push / pull)

Kits are OCI artifacts, so any container registry (GHCR, Docker Hub, ACR…) can host them.

```bash
sbx kit push ./kits/tools-kit docker.io/<you>/tools-kit:1.0
```

> Consume the kit
```bash
sbx run codex . --kit docker.io/<you>/tools-kit:1.0
```

### c) From a git repository

Point `--kit` at a git repo; `#ref=` picks a branch/tag/commit and `#dir=` selects a sub-directory:

```bash
sbx run codex . \
  --kit "git+https://github.com/docker/sbx-kits-contrib.git#ref=v0.1.0&dir=code-server"
```

> `git+ssh://` URLs also work, using your SSH agent / Git credentials.

## 8. Cleanup

```bash
sbx rm codex-kits codex-fromzip
rm -f tools-kit.zip
```

> A kit is **declarative and re-applied** each time (great for versioning and sharing). If instead you want to freeze the *current state* of a sandbox (tools already installed) into a reusable image, use a **snapshot**, see `05-02.snapshots.md`.
