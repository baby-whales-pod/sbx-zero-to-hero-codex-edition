# Local MCP gateway — give the agent tools (no auth)
> `sbx` without ai governance policy

> [!NOTE]
> In this lesson you will force `sbx` to use its **local MCP gateway**, register two **public, no-auth MCP servers** — **DeepWiki** and **Context7** — and use them from the Codex agent to answer questions about a GitHub repo and to fetch up-to-date library docs.

> [!IMPORTANT]
> The `sbx mcp` command group requires a recent `sbx` build. If `sbx mcp status` reports *"command not found"*, your `sbx` predates this feature — upgrade first (this workshop was authored on newer builds; see the version note in the README).

## Why MCP — and why the *local* gateway?

**MCP (Model Context Protocol)** lets the agent call external **tools/servers** (web fetch, docs lookup, a database, a browser…) through a single **gateway** that `sbx` wires into the agent automatically. Just like secrets (see [`03-02.secrets-injection.md`](./03-02.secrets-injection.md)), the agent authenticates to the gateway with a **`proxy-managed` placeholder**, never a real token.

`sbx` can route MCP through a **hosted (cloud) gateway** or a **local data-plane gateway** that runs inside `sandboxd` on your own machine. For this workshop we force the **local** one: it needs **no Docker cloud control plane** and works fully offline-of-SaaS. Combined with **public, no-auth servers**, you get a complete MCP demo with **zero credentials to manage**.

## 1. Force the local gateway

First, make sure `SBX_MCP_URL` is **not set** in your environment — if it is, unset it now and remove it from your shell profile (`~/.bashrc`, `~/.zshrc`, …):

```bash
unset SBX_MCP_URL
```

Then tell `sbx` to always use the local data-plane gateway:

```bash
sbx settings set mcp.forceLocalGateway true
```

Stop and restart the daemon so the new setting takes effect:

```bash
sbx daemon stop
sbx daemon start -d
```

Confirm the mode:

```bash
sbx mcp status
# -> Gateway mode: local
```
**🖐️ this command does not exist anymore**

## 2. Register the two public MCP servers

Both are remote HTTP MCP endpoints. Registration is host-global (they become available to attach to any sandbox).
The second one needs an **authentication**.

```bash
# DeepWiki (Cognition) — ask questions about any public GitHub repo
sbx mcp add deepwiki --url https://mcp.deepwiki.com/mcp

# Context7 (Upstash) — fetch up-to-date documentation for libraries/frameworks
sbx mcp add context7 --url https://mcp.context7.com/mcp
```

> The exact URLs can change over time — if a registration fails, check the provider's current MCP endpoint. Neither server requires `sbx mcp auth` because neither uses OAuth.

Check they are registered:

```bash
sbx mcp ls
sbx mcp inspect deepwiki
```

## 3. Attach them to a sandbox

Create a fresh sandbox with both servers attached from the start (`--static-mcp` takes a comma-separated list):

```bash
sbx run codex . --static-mcp deepwiki,context7 --name codex-mcp
```

> Already have a **running** sandbox? Attach a server live instead — the agent picks it up immediately (via `tools/list_changed`), no restart:
> ```bash
> sbx mcp load deepwiki --sandbox codex-hello-sbx
> ```

## 4. Use DeepWiki from the agent

DeepWiki exposes tools to read and question the "wiki" it builds for any public GitHub repository. Ask the agent:

```text
Using the DeepWiki MCP tools, summarize what the repository microsoft/vscode does,
and list its main components.
```

```text
Using DeepWiki, ask: "how does authentication work in the repository cli/cli?"
```

The agent calls DeepWiki through the local gateway, gets the answer, and reports back — you never handed it any token.

## 5. Use Context7 from the agent

Context7 fetches current, version-accurate documentation for a library. Ask the agent:

```text
Using the Context7 MCP tools, get the latest documentation for the "Hono" web framework
and show me a minimal example of a GET route returning JSON.
```

```text
Using Context7, look up how to define a table with Drizzle ORM and show the code.
```

Context7 typically resolves the library id first, then returns the docs — the agent chains those tool calls for you.

## 6. Verify what the agent sees

You can confirm the servers are wired in from the agent side:

```text
List the MCP servers and tools you currently have access to.
```

Or from the host:

```bash
sbx mcp ls
sbx exec codex-mcp -- bash -lc 'printenv MCP_GATEWAY_URL'   # the gateway the agent talks to
```

## 7. Troubleshooting — network policy

The gateway's outbound call to a remote MCP server goes through the proxy, so if a tool call is blocked (HTTP 403), allow the server's domain in the network policy (see [`04-01-local-policies.md`](./04-01-local-policies.md)):

```bash
sbx policy allow network mcp.deepwiki.com,mcp.context7.com
```

## 8. Cleanup

```bash
sbx rm codex-mcp

# unregister the servers when you no longer need them
sbx mcp rm deepwiki
sbx mcp rm context7
```

> **In short:** `mcp.forceLocalGateway true` + a restart gives you an MCP gateway that runs entirely on your machine; register public no-auth servers with `sbx mcp add … --url …`, attach them with `--static-mcp` (or `sbx mcp load`), and the agent gains new tools — authenticating to the gateway with a placeholder, never a real secret.
