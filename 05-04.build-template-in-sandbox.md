# Build a template without Docker on your host
> `sbx` without ai governance policy

> [!NOTE]
> In this lesson you will build a template image **inside a sandbox** using its built-in Docker engine — no Docker needed on your host — save it to a tar in the mounted workspace, then load it into the sbx template store and run a sandbox from it.

> 📖 Reference: <https://docs.docker.com/ai/sandboxes/customize/templates/>

In `05-03` we built the template image with the **host** `docker` CLI. **But what if you don't have a usable Docker CLI/daemon on your machine?**

Good news: **every sbx sandbox ships its own full Docker Engine** (client + daemon + `/var/run/docker.sock`). So you can build the image **inside a sandbox**, then hand it to the sbx template store.

> ℹ️ **Two separate Docker engines.** The engine *inside a sandbox* (where you build) is **not** the sbx runtime's template store (what `sbx template ls` shows). The bridge between them is the **mounted workspace**: save the image to a tar in the workspace (visible on the host), then `sbx template load` it.

We reuse the exact same `custom-template/Dockerfile` from `05-03` (`FROM docker/sandbox-templates:codex-docker` + `figlet` + `python3`).

## 1. Confirm a sandbox has Docker

Any existing sandbox works. From an earlier lesson:

```bash
sbx exec codex-hello-sbx -- docker version
```

You should see both a **Client** and a **Server** section — a real engine, not just the CLI.

## 2. Create a builder sandbox over the Dockerfile

Make sure `custom-template/Dockerfile` from `05-03` is in the current directory, then create a `shell` sandbox on it:

```bash
sbx create shell . --name builder
```

> The workspace is mounted **at the same absolute path** as on the host, and `sbx exec` starts in it — so `custom-template/` is right there inside.

## 3. Build the image *inside* the sandbox

The build uses the sandbox's own Docker engine (it pulls the base from `docker.io` — make sure your network policy allows it, see `04-01`):

```bash
sbx exec builder -- sh -c 'cd custom-template && docker build -t my-codex-tools:v1 .'
```

Check it landed in the sandbox's inner engine:

```bash
sbx exec builder -- docker images my-codex-tools
```

## 4. Export the image to the workspace (the bridge to the host)

`docker save` inside the sandbox, writing the tar into the workspace root so it appears on the host:

```bash
sbx exec builder -- sh -c 'docker save my-codex-tools:v1 -o my-codex-tools.tar'

# it is now visible on the host (bind-mounted workspace):
ls -lh my-codex-tools.tar
```

## 5. Load it into the sbx template store (on the host)

```bash
sbx template load my-codex-tools.tar
sbx template ls | grep my-codex-tools
```

Now use it like any template:

```bash
sbx run codex . -t my-codex-tools:v1 --name codex-builtinsbx
sbx exec codex-builtinsbx -- figlet "built in a sandbox"
sbx exec codex-builtinsbx -- python3 --version
```

## 6. 🐳 Alternative — push to a registry from inside the sandbox

If you have a registry, skip the tar dance entirely — build **and** push from inside the sandbox, then let sbx pull it:

```bash
# inside the sandbox
sbx exec -it builder -- bash
#   docker login docker.io
#   cd custom-template
#   docker build -t docker.io/<you>/my-codex-tools:v1 --push .
#   exit

# on the host
sbx run codex . --template docker.io/<you>/my-codex-tools:v1 --name codex-fromdockerfile
```

## 7. Cleanup

```bash
# sandboxes
sbx rm builder codex-fromdockerfile

# template + workspace artifact
sbx template rm my-codex-tools:v1
rm -f my-codex-tools.tar
```

> 🧭 Recap of the three build/prepare paths:
> - **`05-03`** build with the **host** Docker → `save`/`load` or `--push`
> - **`05-04`** (this one) build **inside a sandbox** when the host has no Docker
> - **`05-02`** don't build at all — **snapshot** a sandbox you set up by hand
