# Custom template from a Dockerfile
> `sbx` without ai governance policy

> [!NOTE]
> In this lesson you will bake your own sandbox image from a Dockerfile — with your tools pre-installed — using the host `docker` CLI, register it as a reusable `sbx` template, and create a sandbox from it.

> 📖 Reference: <https://docs.docker.com/ai/sandboxes/customize/templates/>

> [!IMPORTANT]
> This lesson requires a working **Docker CLI and daemon on your host** — the `docker build` (and optional `docker save` / `docker login … --push`) commands below run on your machine, not inside a sandbox. Check with `docker version` (both Client and Server must respond). If you don't have Docker on your host, skip to [`05-04.build-template-in-sandbox.md`](./05-04.build-template-in-sandbox.md), which builds the exact same template **inside a sandbox** using its built-in Docker engine.

So far we prepared sandboxes at **runtime** (kits, `05-01`) or by **snapshotting** a running sandbox (`05-02`). A third way is to **bake your own image with a Dockerfile** and use it as a template; this is the cleanest option when you want a reproducible, version-controlled base with your tools pre-installed.

We reuse the same tools as the kit lesson: **`figlet`** and **`python3`**.

## 1. How sbx templates work

- Every sandbox image extends a published base: `docker/sandbox-templates:<variant>`. They are **Ubuntu-based** and run as a **non-root `agent` user with sudo**.
- The **agent** is decided by the base image variant **and** the agent you pass to `sbx run` — *not* by binaries in your image.


## 2. Write the Dockerfile

Create a folder and a `Dockerfile`:

```bash
mkdir -p custom-template
```

`custom-template/Dockerfile`:

```dockerfile
# Extend the codex sandbox base image
FROM docker/sandbox-templates:codex-docker

# root for system packages...
USER root
RUN apt-get update \
 && apt-get install -y --no-install-recommends figlet python3 \
 && rm -rf /var/lib/apt/lists/*

# ...then ALWAYS switch back to the agent user
USER agent
```

> ✋ Golden rule: use `USER root` for `apt-get`, then switch back to `USER agent` before finishing (and for any user-level tool install, e.g. `curl … | sh` for rustup, `npm i -g …`, etc.).

## 3. Build the image

Standard Docker build on your host (this pulls the base image the first time. It can take a few minutes):

```bash
docker build -t my-codex-tools:v1 ./custom-template
```

## 4a. Use it locally (no registry)

> **Important:** `sbx` has its **own image store**, separate from your host Docker. An image you just built on the host is *not* visible to `sbx` yet; you must export it and load it in.

```bash
# export the host image to a tar
docker save my-codex-tools:v1 -o my-codex-tools.tar

# import it into the sbx image store
sbx template load my-codex-tools.tar

# confirm it is now a usable template
sbx template ls
```

Now create a sandbox **from your template** with `-t` / `--template`:

```bash
sbx run codex . -t my-codex-tools:v1 --name codex-fromdockerfile
```

## 4b. Or share it via a registry

Building with `--push` publishes straight to a registry; `sbx` then pulls it into its store on first use — no `save`/`load` needed:

```bash
docker login docker.io
docker build -t docker.io/<you>/my-codex-tools:v1 --push ./custom-template

# on any machine
sbx run codex . --template docker.io/<you>/my-codex-tools:v1 --name codex-fromdockerfile
```

## 5. Verify your tools are baked in

No install step at runtime — the tools are already in the image:

```bash
sbx exec codex-fromdockerfile -- figlet "from Dockerfile"
sbx exec codex-fromdockerfile -- python3 --version
```

Ask the agent too:

```text
please run: figlet "from Dockerfile"
```

## 6. Combine a template with a kit

A Dockerfile template bakes **tools at build time**; a **kit** adds **runtime behavior** (startup commands, files). They compose nicely: reuse the launcher kit from `05-01` to start an HTTP server on the tools already in the image:

```bash
sbx run codex . \
  -t my-codex-tools:v1 \
  --kit ./kits/serve-kit \
  --name codex-tpl-plus-kit

# publish and test (IPv4 — see 05-01)
sbx ports codex-tpl-plus-kit --publish 7070:7070/tcp
curl http://127.0.0.1:7070/
```

## 7. When to use what

| Approach                | What it is                          | Best for |
|-------------------------|-------------------------------------|----------|
| **Dockerfile template** | a versioned base image you build    | reproducible, shared base with pre-installed tools |
| **Snapshot** (`05-02`)  | freeze a running sandbox to an image| "capture what I just set up by hand" |
| **Kit** (`05-01`)       | declarative artifact, re-applied    | runtime startup, files, per-run tweaks, easy sharing |

## 8. Cleanup

```bash
sbx rm codex-fromdockerfile codex-tpl-plus-kit

# remove the template from the sbx store
sbx template rm my-codex-tools:v1

# host-side artifacts
docker rmi my-codex-tools:v1
rm -f my-codex-tools.tar
```
