# Container escape — why sandboxes matter
> ## ✋ Disclaimer: this is a teaching demo, not security advice 🤓

## What is a "container escape"?

A container is *supposed* to be isolated from its host. A **container escape** is when code running **inside** a container manages to read, modify, or execute things **on the host** — breaking out of that isolation.

The scariest part: you often don't need a fancy kernel exploit. The most common "escape" is simply a **dangerous `docker run` flag**. Mount the host root into a container and the container can walk your entire disk:

```bash
docker run -it --rm -v /:/host_root some-image sh
# now /host_root inside the container IS your host filesystem
```

> 🤖 **Why this matters for AI agents.** *If you can do it manually, chances are your agent can do it too.* An agent you let run `docker` on your machine — or a random image whose origin you don't know — can do exactly this. Running the agent inside `sbx` (an isolated VM that only mounts the workspaces you declare) is what stops the blast radius from reaching your whole host.

## The demo

We build a plain Alpine image and use it as an *innocent-looking* container that turns out to have full access to the host.

### 1. Build the image

Create a `Dockerfile` with this content:

```dockerfile
FROM alpine:3.12
```

Then build it:

```bash
docker build -t alpine-from:somewhere .
```

### 2. Plant a "classified" file on the host

```bash
echo "🤐 hello, this is classified" > ~/host-file.txt
cat ~/host-file.txt
```

### 3. Escape into the host filesystem 😈

**Very bad practice — do this only in this demo, at your own risk.** Mount the whole host root (`/`) into the container:

```bash
docker run -it --rm -v /:/host_root alpine-from:somewhere sh
```

You are now in the container. **Where your host file appears depends on your OS**, because Docker Desktop (macOS/Windows) runs a hidden Linux VM, while Docker on Linux shares the host kernel directly.

---

#### 🐧 Linux (native Docker Engine)

No VM in between — `/host_root` **is** your real host root, so your home directory is right there:

```sh
# inside the container (replace k33g with your host user)
cat /host_root/home/k33g/host-file.txt

# and you can WRITE to the host too:
echo "👋😈 I was here" >> /host_root/home/k33g/host-file.txt
```

> ⚠️ On Linux this is the most direct escape: the container runs as `root`, so it writes host files **as root** — it can even touch `/etc`, `/root`, SSH keys, etc.

#### 🍏 macOS (Docker Desktop)

Docker Desktop bind-mounts your Mac filesystem inside its Linux VM under `/host_mnt`, so your home directory lives at `/host_root/host_mnt/Users/...`:

```sh
# inside the container (replace k33g with your macOS user)
cat /host_root/host_mnt/Users/k33g/host-file.txt

echo "👋😈 I was here" >> /host_root/host_mnt/Users/k33g/host-file.txt
```

#### 🪟 Windows (Docker Desktop, WSL2 backend)

Docker Desktop exposes your Windows drives inside its VM under `/run/desktop/mnt/host/<drive-letter>`, so `C:\Users\...` becomes `/host_root/run/desktop/mnt/host/c/Users/...`:

```sh
# inside the container (replace k33g with your Windows user)
cat /host_root/run/desktop/mnt/host/c/Users/k33g/host-file.txt

echo "👋😈 I was here" >> /host_root/run/desktop/mnt/host/c/Users/k33g/host-file.txt
```

> 💡 You can also bind-mount a single Windows drive directly, e.g. `docker run -it --rm -v //c/Users/k33g:/host_root alpine-from:somewhere sh`, and then read `/host_root/host-file.txt`.

---

### 4. Back on the host — see the damage

Exit the container (`exit`) and check the file on your host:

```bash
cat ~/host-file.txt
# -> 🤐 hello, this is classified
# -> 👋😈 I was here     <-- written from *inside* the container
```

The container reached out and modified a host file. That is the escape.

## How to prevent this

- 🔥 **Never use `-v /:...`** — do not mount the host root (or other sensitive dirs like `~/.ssh`, `~/.aws`, `/etc`).
- Only mount **exactly** what the container needs.
- Prefer **read-only** mounts with the `:ro` flag when write access isn't required:

  ```bash
  docker run -it --rm -v /:/host_root:ro alpine-from:somewhere sh
  # 😡 can still READ the host FS...
  # 🙂 ...but writes now fail: "Read-only file system"
  ```

- Be **even more careful** with images whose **origin you don't trust**.
- ✅ **Best of all for AI agents: don't give them raw `docker`/host access.** Run them inside `sbx`, which isolates the agent in a VM and only exposes the workspaces you explicitly mount — the rest of your host stays invisible. This is exactly what the next modules demonstrate.
